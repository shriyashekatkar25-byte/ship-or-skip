The decision on the table

Framed the way it would land in a product review: who it's for, what success means, and what we refuse to break.

Customer problem

Wrong first answer, lost trust

Business users ask questions in plain English and expect the first answer to be right. When the top-ranked answer misses, they stop asking and go back to filing tickets with the data team.

The change (variant B)

Re-rank with table usage signals

Candidate answers get boosted when they use tables that are certified, frequently queried and recently refreshed. Control (A) ranks by model confidence alone.

Success metric

Answer acceptance rate

Share of questions where the user accepts the first answer: they click thumbs-up, save it to a dashboard, or don't rephrase within 60 seconds.

The director memo

Written live from the simulation above. Change the scenario and the memo rewrites itself, because a good memo states the evidence it's standing on.

Launch decision: answer re-ranking

Decision
Evidence
Why this rule
We ship when B is very likely better and the cost of being wrong is small. A significance test only answers "is there any difference?" Expected loss answers the question leadership asks: "if we're wrong, how much does it hurt?"
Risks
  • Novelty effect: users may click a fresh ranking more at first. Compare week 1 and week 2 lift before calling it.
  • Segment mix: analysts and business users may react differently. Check the lift holds in both before full rollout.
  • Governance: boosting "popular" tables must never surface restricted data. Permission checks happen before ranking, and an audit query backs it up.
Rollout
5% of workspaces → 25% → 100%, with a kill switch if any guardrail breaches for 2 consecutive days. The posterior from this test becomes the prior for the next stage, so evidence carries forward.

04

The math, from my Monte Carlo course

Two ideas from UCLA Stats 102C carry this whole room. Explained in my own words with a product example.

Bayesian updating · conjugate priors

Beliefs as a Beta distribution

Treat each arm's true acceptance rate as uncertain and describe it with a Beta(a, b) curve. Think of a as "acceptances we've effectively seen" and b as "misses we've seen". When k of n new questions are accepted, the update is just addition:

Beta(a, b) → Beta(a + k, b + n − k)

The prior is how much past launches should count. A strong prior needs more data to move, which protects against getting excited about one lucky day.

Monte Carlo · estimate by simulation

Turning curves into decisions

"Chance B beats A" has no tidy formula. So we draw 20,000 plausible worlds: sample a rate for A, sample one for B, and record who won and by how much. Averages over those worlds give us:

  • P(B > A): the share of worlds where B wins.
  • Expected loss: the average shortfall in worlds where B actually loses. That's the price of shipping a mistake.

More draws make these numbers steadier. Error shrinks with the square root of the number of draws.

How I'd run it on real logs

The same analysis against an event table in a lakehouse. The table and columns are illustrative.

-- Daily acceptance by arm (SQL)
SELECT
  experiment_arm,
  COUNT(*)                                  AS questions,
  SUM(CASE WHEN accepted THEN 1 ELSE 0 END) AS accepted,
  PERCENTILE(latency_ms, 0.95)              AS p95_latency_ms
FROM analytics.assistant_answer_events
WHERE experiment_id = 'answer_rerank_v2'
  AND event_date >= '2026-10-01'
GROUP BY experiment_arm;
# Decision rule (Python)
import numpy as np
rng = np.random.default_rng(102)
a0, b0 = 42, 58              # prior from past launches
A = rng.beta(a0 + kA, b0 + nA - kA, 20_000)
B = rng.beta(a0 + kB, b0 + nB - kB, 20_000)
p_b_wins = (B > A).mean()
exp_loss = np.maximum(A - B, 0).mean()
ship = p_b_wins > 0.95 and exp_loss < 0.002
